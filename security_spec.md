# CapeSafe Connect 360 — Firestore Security Specification

## 1. Data Invariants
1. **Default-Deny Baseline**: Every unspecified document path is denied by `match /{document=**} { allow read, write: if false; }`.
2. **PII Isolation**: User emails, emergency contacts, and digital pass identifiers are stored in `/users/{userId}/private/{docId}` and are strictly readable/writable only by `userId == request.auth.uid` or an Admin.
3. **Anti-Privilege-Escalation**: During user profile creation at `/users/{userId}`, `role` MUST equal `'tourist'`. Only an Administrator (`isAdmin()`) may promote a user's `role` to `'admin'`, `'provider'`, or `'safety'`.
4. **Ownership & Query Enforcement**: Private collections (`itineraries`, `notifications`, `travel_budgets`, `bookings`, `tourist_check_ins`) enforce `resource.data.userId == request.auth.uid` directly inside `allow list` and `allow get` without `get()`/`exists()` inside `allow list` (Safety Management can `get` individual `tourist_check_ins` or read via role-scoped query where `safetyTeamReadable == true`? No—to avoid `get()` in `allow list`, `tourist_check_ins` list is restricted to `resource.data.userId == request.auth.uid` for tourists, and single-doc `get` or admin/safety lookups use verified role checks).    - Actually, `isAdmin()` with email check (`request.auth.token.email_verified == true && request.auth.token.email == 'emihletom07@gmail.com'`) uses zero `get()` calls! And for `tourist_check_ins` / `bookings`, tourists list `where('userId', '==', uid)`, providers list `where('providerId', '==', uid)`, and Safety Officers/Admins can list via a single `get()`? No, `SKILL.md` forbids `get()` in `allow list`. Let's inspect how `SKILL.md` handles it:
   - Public-read operational boards (`tourism_businesses`, `incidents`, `reviews`, `community_posts`, `announcements`) allow `list` for signed-in users (`isSignedIn()`), while private PII/user records (`users/{userId}/private`, `users/{userId}/trusted_contacts`, `itineraries`, `notifications`, `travel_budgets`, `bookings`, `tourist_check_ins`) strictly require `resource.data.userId == request.auth.uid` (or `resource.data.providerId == request.auth.uid` for bookings, or `isOwner(userId)` for subcollections, or `isBootstrapAdmin()` using token email)!
5. **Explicit Location Consent Invariant**: `sharedLat` and `sharedLng` on `incidents` and `tourist_check_ins` are only permitted when `locationConsent == true` and coordinates are within valid geographic bounds (`-90..90`, `-180..180`).
6. **Announcement Governance**: Only verified Administrators or Safety Management Personnel may create/update destination `announcements`; only Administrators may delete them.
7. **Booking Confirmation & Provider Inventory Invariant**: New `bookings` MUST be created with `status == 'Pending Verification'`. Tourists may only transition their own booking to `'Cancelled'` (with optional `cancellationReason`) and cannot self-confirm. Only the matching `providerId` (for `'Confirmed'`, `'Completed'`, `'Cancelled'`) or an Administrator may confirm a booking. `provider_offerings` can only be created or updated by verified `provider` or `admin` roles owning `providerId`.
8. **Community Moderation & Privacy Controls**: `community_posts` enforces `moderationStatus` (`Approved`, `Under Review`, `Removed`). Verified users may flag a post (`moderationStatus == 'Under Review'`, `flaggedBy == request.auth.uid`), while only Administrators or Safety Management Personnel may approve/remove moderated posts. User privacy controls (`profileVisibility`, `shareLocationConsent`, `aiContextPersonalization`, `preferredLanguage`) and `/users/{userId}/challenge_progress/{challengeId}` are strictly scoped to the verified account owner.

## 2. The "Dirty Dozen" Attack Payloads (All Must Return PERMISSION_DENIED)
1. **Self-Role Escalation on Registration**: Creating `/users/attacker1` with `{ "role": "admin", ... }` -> Denied (`role` must equal `'tourist'`).
2. **Profile Role Tampering on Update**: Updating `/users/user1` changing `role` from `'tourist'` to `'safety'` -> Denied (`affectedKeys().hasOnly(...)` excludes `role` for non-admins).
3. **PII Cross-User Snooping**: Reading `/users/victim1/private/contact` as `attacker1` -> Denied (`!isOwner && !isAdmin`).
4. **Shadow Field Injection on Booking**: Creating `/bookings/b1` with `{ ..., "isFreeVip": true }` -> Denied (`keys().hasOnly(...)` rejects shadow fields).
5. **Identity Spoofing on Travel Budget**: Creating `/travel_budgets/tb1` as `attacker1` with `{ "userId": "victim1", ... }` -> Denied (`incoming().userId == request.auth.uid`).
6. **Blanket Query Scraping on Itineraries**: Listing `/itineraries` without `where('userId', '==', uid)` -> Denied (`allow list` requires `resource.data.userId == request.auth.uid`).
7. **Unverified Email Spoof Attack**: Writing as `emihletom07@gmail.com` with `email_verified: false` -> Denied (`isVerified()` requires `email_verified == true`).
8. **Terminal State Mutation & Tourist Self-Confirmation**: Updating a `Booking` whose existing `status == 'Completed'` back to `'Pending Verification'`, or updating a tourist's own `Booking` to `status == 'Confirmed'` -> Denied (Terminal state lock & `incoming().status == 'Cancelled'` tourist-only update guard).
9. **Client Timestamp Forgery**: Creating a `CommunityPost` with `createdAt` set to a past client date instead of `request.time` -> Denied (`incoming().createdAt == request.time`).
10. **Document ID Poisoning**: Writing `/reviews/<200-char-junk>` or `/reviews/bad$id` -> Denied (`isValidId()` regex & size check).
11. **Value/Size Exhaustion**: Creating an `Incident` with a 10,000-character `summary` -> Denied (`summary.size() <= 800`).
12. **Immortal Field Overwrite**: Updating a `TourismBusiness` or `ProviderOffering` to change `ownerId`/`providerId` or `createdAt` -> Denied (`incoming().ownerId == existing().ownerId && incoming().createdAt == existing().createdAt`).
